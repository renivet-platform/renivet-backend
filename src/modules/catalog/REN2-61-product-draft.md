# REN2-61 progressive product drafts

`POST /api/v1/brands/{brandId}/products` creates a parent draft from a style code, title, category code, and exact published category schema version. Draft creation does not require prices, images, variants, or required submission attributes. The optional initial variants use the candidate `CreateVariant` shape; REN2-62 owns later variant CRUD. Titles and free text are trimmed and normalized to Unicode NFC; category selection must be an active leaf and the requested historical or current schema version must be published.

`PATCH /api/v1/brands/{brandId}/products/{productId}` merges supplied title, description, category schema version, and product attributes. Each successful update requires the quoted decimal row version in `If-Match`, increments both `row_version` and `content_version`, and writes only a DRAFT or INCOMPLETE product. A stale row version returns 409. Attribute values are validated and persisted against frozen rule IDs for the selected version; absent required submission values remain valid during draft saves.

Both mutations require W1 `catalog.write`, a first-party session, allowlisted same-origin request metadata, a session-bound CSRF token, and an `Idempotency-Key`. The repository repeats live permission and approved-brand checks in its write statements. Brand onboarding states other than `approved`, suspended/revoked memberships, cross-brand product IDs, archived/restricted products, and invalid category pins fail closed. Idempotent receipts commit with the product mutation; replaying the same key and payload returns the original response, while a changed payload conflicts.

Migration `0011_ren2_61_product_draft_lifecycle.sql` defines `catalog.write` without granting it to a role, adds transactional mutation receipts, and records field lineage with `MANUAL` or `IMPORT` source kinds. Migration `0012_ren2_61_product_draft_receipt_immutability.sql` makes mutation receipts and field lineage append-only. The HTTP routes record manual edits; import processing can supply its batch reference through the repository context when that later slice is implemented. Role grants remain controlled by the approved W1 permission matrix.
